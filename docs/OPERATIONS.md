# Эксплуатация Startify Sprint 0.3

Это руководство для **одного пилотного процесса**, а не заявление о готовности к 100 000 одновременных пользователей. Горизонтальное масштабирование требует общего хранилища сессий/лимитов и миграции с локального SQLite.

## Развёртывание без контейнера

Node.js 22.13+, Linux, HTTPS reverse proxy. Секреты задавайте через менеджер секретов или `.env` с правами `0600`, не через историю команд.

```bash
npm ci --ignore-scripts
npm run format:check
npm test
npm run build
npm audit
# Заполните .env по .env.example: DEMO_MODE=false, SEED_DEMO=false,
# ORGANIZER_PASSWORD, CHALLENGE_ACCESS_CODE, APP_ORIGIN=https://ваш-домен
npm start
```

Для существующей БД `SEED_DEMO` не добавляет историю задним числом. Для нового чистого пилота используйте новый путь `DB_PATH` и не копируйте демо-БД. Сервер применяет идемпотентные миграции схемы при старте. Сделайте резервную копию перед обновлением.

На одном доверенном reverse proxy установите `TRUST_PROXY=1`. Не открывайте приложение напрямую в обход proxy: иначе заголовок `X-Forwarded-For` можно подменить. Proxy должен передавать исходный Host либо настройте точный `APP_ORIGIN`. HTTPS terminate на proxy; `COOKIE_SECURE=true`. HMR отключён, наружу нужен только основной HTTP-порт.

## Контейнер

```bash
# .env: приватные ORGANIZER_PASSWORD и CHALLENGE_ACCESS_CODE
docker compose up --build -d
docker compose logs --tail 50 app
```

Образ многоступенчатый, запускается от `node`, без dev-зависимостей; compose использует read-only rootfs, отдельные volumes для БД и копий, healthcheck и 15 секунд на graceful shutdown. Порт публикуется только на `127.0.0.1:3000`: TLS/reverse proxy настройте отдельно. `COOKIE_SECURE=false` допустим только для локальной проверки HTTP.

SmallThinker по умолчанию выключена. URL `http://host.docker.internal:8080/v1` обращается к серверу **на хосте**, не к браузеру пользователя. Remote endpoint должен использовать HTTPS. Модель и веса разворачиваются отдельно по [SMALLTHINKER.md](SMALLTHINKER.md).

Dockerfile/compose добавлены в репозиторий; их запуск нужно проверить на целевом Docker-хосте. Наличие файлов само по себе не означает, что образ уже опубликован или проверен в этом окружении.

## Резервное копирование и восстановление

```bash
npm run backup -- ./backups
# В контейнере:
docker compose exec app node scripts/backup.js /app/backups
```

Используется online backup API SQLite: committed WAL-страницы включаются в единый `.db`-файл. Копия проверяется `integrity_check` и `foreign_key_check`, создаётся с правами `0600`. Простое копирование только `.db` во время работы **не является надёжной резервной копией**.

- Храните копии вне публичного каталога и вне единственного диска приложения; шифруйте при передаче.
- В копиях есть учебные заметки, хеши ключей и сессии. Доступ — только у доверенного администратора.
- Начальная политика пилота: ежедневная копия, 7 ежедневных и 4 еженедельных поколения. Ретенцию и отправку в защищённое внешнее хранилище настройте в scheduler; скрипт сам чужие старые файлы не удаляет.
- Восстановление: остановите приложение → сохраните повреждённую БД отдельно → проверьте копию → положите её по `DB_PATH` → убедитесь, что старые `-wal`/`-shm` не относятся к другой БД → задайте владельца `node` → запустите один процесс → проверьте health и вход.
- Еженедельно выполняйте тестовое восстановление на отдельном пути. Измеряйте фактические RPO/RTO; целевые для пилота RPO ≤24 ч, RTO ≤1 ч, а не гарантированные SLA.

## Наблюдаемость и остановка

JSON-логи stdout содержат метод, маршрут API, статус и длительность. Не пишутся cookie, query string, текст заметок, промпты и ключи. Ошибки 500 не раскрывают наружу SQL или содержимое модели. Настройте сбор stdout, срок хранения и алерты на 5xx/429, недоступность health, нехватку диска и рост очереди проверки.

`GET /api/health` — liveness процесса, **не** гарантия доступности внешнего LLM. Проверка модели — отдельная кнопка организатора или `npm run llm:check`.

SIGTERM/SIGINT перестаёт принимать новые соединения, ожидает текущие запросы до 10 секунд, закрывает Vite/таймеры, выполняет WAL checkpoint и закрывает БД. При превышении лимита процесс завершается с ошибкой; дайте контейнеру ≥15 секунд. In-memory лимиты и очередь LLM не переживают рестарт; durable-квота LLM сохраняется в SQLite.

## Нагрузка и честные границы

- `/api/bootstrap`: лёгкие сводные SQL-метрики и первые 50 проектов; `totalProjects` — реальное общее число.
- `/api/projects?q=&country=&category=&limit=24&offset=0`: серверная фильтрация и пагинация, максимум 100 на страницу.
- `/api/organizer?limit=50&offset=0`: страницы команд и очереди, но глобальные метрики. Кабинет загружает следующие страницы явно. Поиск в таблице ищет среди **загруженных** команд; полный экспорт CSV проходит все страницы.
- `/api/organizer/audit`: журнал ручных решений с комментарием и чек-листом. Это журнал приложения, не юридически неизменяемый аудит; общий пароль не даёт персональной атрибуции нескольким организаторам.
- Индексы для витрины, очереди, активации и дневной квоты; проверка актуального состояния перед сохранением в write transaction; учёт параллельных запросов к оставшейся LLM-квоте.
- Перед большим пилотом нужны нагрузочный тест, отдельные аккаунты организаторов/RBAC, модерация контента, согласованные политики хранения/удаления, внешний monitoring и проверенный disaster recovery.
- Цель роста 100 000 участников — накопительная за сезон, не обещание 100 000 concurrent connections. Базовый сценарий 96 000 новых участников + 4 000 исходных даёт прогноз 14 045 публикаций, а не измеренный результат.
